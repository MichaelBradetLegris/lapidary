# CLAUDE.md

Lapidary (formerly Stet) is a desktop app for reviewing AI-suggested copyedits to novel chapters stored as Markdown in an Obsidian vault. The full design and phase plan is in `PLAN.md`. Read it before starting any phase and tick its checkboxes as phases land.

## Stack

Electron + electron-vite + React + TypeScript. AI reviews go through a provider layer in `src/main/providers/` (one `ReviewProvider` interface, one set of `ai:*` IPC channels). Claude is called only by running the Claude Code the user installed (`src/main/providers/claudeCli.ts`, flags in `claudeOptions.ts`); the app ships nothing of Anthropic's, neither a binary nor a library; OpenAI only through the official `openai` package's Responses API, for ChatGPT (`src/main/providers/chatgpt.ts`, `codex.3`, PLAN 5.8; the request is `providers/openai.ts`'s), with the Sign in with ChatGPT access token as the bearer, renewed in `src/main/chatgpt` and never kept by the provider; reviews on an OpenAI API key went in `codex.6`. All run in the Electron main process. Text algorithms live in `src/shared` and are pure TypeScript with vitest coverage.

The app's display name is `APP_NAME` in `src/shared/branding.ts` and nowhere else; the same file holds `APP_ID` and `APP_REPOSITORY`, both frozen from 1.0, and `scripts/branding.cjs` reads all three for the build. The window title, `index.html` (through a vite `transformIndexHtml` plugin), `package.json`'s `productName`, `repository`, `homepage` and `bugs` (through `scripts/sync-branding.cjs`, run by `npm run package` and checked by `npm run branding:check`) and the electron-builder config all read it from there, so renaming the app is one edit. `APP_DATA_DIR` in the same file pins the userData folder to a name of its own, so a rename never moves the author's settings or their saved reviews. The icon is generated from one geometry spec by `scripts/make-icons.py` into `resources/icon/`.

Every colour the renderer paints is a token, a custom property in `src/renderer/styles/app.css` (PLAN 11.3 e), and the rules name colours only through tokens. The tokens are set twice at the top of that file: the light block is the top-level `:root`, the dark block the `:root` inside `@media (prefers-color-scheme: dark)`, each with its own `color-scheme`, and every token is in both except the two fonts, which are the same in both themes and stay in the light block. The Appearance setting reaches that media query through `nativeTheme.themeSource` (`applyTheme` in `src/main/theme.ts`; no data attribute and no IPC of its own, C.50), and `WINDOW_BACKGROUND` in `src/shared/ui/theme.ts` repeats each block's `--bg` for the window behind the page, which `test/shared/theme.test.ts` checks. So a new colour is a new token with a value in both blocks, never a colour in a rule or in code. `test/renderer/themeContrast.test.ts` is the contrast test: it reads both blocks (`test/helpers/themeTokens.ts`) and holds each pair to 4.5:1 for text and 3:1 for faint text and marks in each theme, with tints composited as `color-mix()` paints them (`test/helpers/contrast.ts`); a new token gets its pairs there. `test/renderer/themeCss.test.ts` is the colour guard. It fails on a hex colour or a colour function in `app.css` outside the two blocks or anywhere in the renderer's code (an `rgb()` whose first argument is a `var()`, as in `rgb(var(--shadow-rgb) / 8%)`, and `color-mix()` of tokens pass), on a named or system colour such as `white` or `Canvas` in a CSS value, on an SVG `fill` or `stroke` other than `none` and `currentColor`, on an inline style key that can carry a colour, on a token in one block and not the other, on a `var()` that names no defined property, and on a scroller whose background is not one token that is an opaque colour in both themes (C.48; a translucent token such as `--hover-overlay` fails). It also pins every value in both blocks, so a value changed on purpose is changed there too, and in the same commit on `theme.4`'s list of light differences in PLAN.md (light) or in 11.3 (e) (dark). Focus rings are the browser's own (`outline: auto`), with four exceptions in `app.css`, which `themeCss.test.ts` lists as the only rules that name an outline: the side panel's split handle draws a 2 px `--accent` ring inside its band (PLAN section 7), the paragraph box shows its focus as a glow of `--accent`, the turquoise of its own border, in place of the ring (`theme.12` kept it on the blue the border had then; `theme.13` turned `--accent` turquoise everywhere, a shade deeper than `--accent-fill`, and gave the You chip its blue as `--cat-you`), Full edit's text area shows its focus as the caret alone, as a page in Google Docs does, with its sheet the same focused and not (`rr.7`: round a text area that fills the sheet the ring would be the bordered box the author asked to lose; `rr.9` took away the faint blue edge `rr.7` gave the sheet, at his ask), and a dialog's box, which takes the focus as it opens, shows none (its controls keep theirs). Text selection has the app's own bands since `polish.1`, two translucent turquoises: `::selection` takes `--selection-bg`, plain to see, and `--selection-ink`, and so do the fields, the paragraph box included (`.prose input::selection, .prose textarea::selection`); `.prose ::selection` takes the faint `--selection-prose-bg`, which a ghost above a selected line needs and a suggestion's underline and tint, the focus and a small change's capsule show through, in `currentColor`, so the prose keeps its own colours (the active find match keeps its dark ink on the dark orange); a filled button and the active Setup tab show no band. Their pairs, the ghosts above a selected line at 4.5:1 and the underline under the prose's band at 3:1 among them, and a floor on how plainly each band shows (a CIELAB difference, and a luminance ratio for `--selection-bg`), are in `themeContrast.test.ts`. Scrollbars are the app's own since `polish.2` (the author's pick, the sheet's D with its thumb a shade darker; C.106): bare `::-webkit-scrollbar` rules in `app.css`, never scoped with `:root` (Chromium then drops the thumb's hover and the arrows), on `--scrollbar-track` and the thumb's `--scrollbar-thumb`, `--scrollbar-thumb-hover` and `--scrollbar-thumb-active`: a 16 px gutter with a 1 px `--border` line, a square thumb, arrows in `--ink-faint`, and in a box with rounded corners the box's corners, written out for each such box and resizable field. The thumb is one of the two marks under 3:1, both by the author's choice; the other is a decided row's two faded buttons (`polish.14`), `--ink-faint` at the share `--row-fade` on the row's three backgrounds, held to 1.35 to 1.9. `themeContrast.test.ts` names each exception by its tokens and no other, holds the thumb's ratios on the track to 1.3 to 1.5 at rest, 1.5 to 1.7 hovered and 1.7 to 2.0 dragged, and `themeCss.test.ts` fails a `scrollbar-color`, or a `scrollbar-width` other than the chips' row's `none`, either of which gives a scroller the browser's bar back. There is no `--focus-ring` token, for the reasons 11.3 (e) gives.

```
npm run dev        # electron-vite dev with HMR

npm test           # vitest
npm run test:slow  # the watcher's timing tests in test/slow/
npm run typecheck
npm run lint
npm run format:check
npm run build      # typecheck, then electron-vite build
npm run package    # sync productName, build, notices, electron-builder into dist/, then verify:package --installer
npm run package:dir     # the same, but only dist/win-unpacked: no installer, and so no app-update.yml
npm run notices         # out/THIRD_PARTY_NOTICES.txt from the build's records; needs build first
npm run verify:package  # check dist/win-unpacked; -- --installer also the installer, latest.yml and app-update.yml
npm run release:check -- v<x.y.z>  # can this tag be released? The release workflow's first step
npm run release:notes -- v<x.y.z>  # that version's CHANGELOG section and .github/release-footer.md
npm run icons      # regenerate resources/icon/ from scripts/make-icons.py (needs Pillow)
npm run branding:check  # exit 1 if package.json has drifted from src/shared/branding.ts; writes nothing
npm run check:public    # exit 1 if a file git would commit holds a profile path, an email or a key shape
```

`npm run dev:clean -- <flags>` (`scripts/dev-clean.cjs`, C.43) removes every variable whose name starts with `CLAUDE`, `ANTHROPIC` or `DISABLE_`, printing their names and never their values, sets `MANUSCRIPT_REVIEW_USER_DATA` to the git-ignored `.dev-userdata`, and sets `REMOTE_DEBUGGING_PORT=9222`, which electron-vite passes to Electron as `--remote-debugging-port`, so DevTools listens on port 9222. Its flags: `--user-data <dir>`, or `--user-data-fresh` for a new empty folder in the system's temp folder, in place of `.dev-userdata`; `--claude-config <dir>`, or `--claude-config-empty` for a new empty folder (Claude Code signed out), as `CLAUDE_CONFIG_DIR`; `--api-key-dummy` and `--auth-token-dummy`, a dummy `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` (C.71); `--no-claude-code`, `--quiet` and `--shell-stub`, which turn on `MANUSCRIPT_REVIEW_DEV_NO_CLAUDE_CODE`, `MANUSCRIPT_REVIEW_DEV_QUIET_WINDOW` and `MANUSCRIPT_REVIEW_DEV_SHELL_STUB` (below); and `--exe <path>`, which runs a packaged build with `--isolated-user-data=<dir>` and `--remote-debugging-port=9222` instead of `electron-vite dev`, and on which those three do nothing. `--help` prints the list. Set `V8_INSPECTOR_PORT=9229` before `dev:clean` to open main's inspector: electron-vite passes it to a development run as `--inspect` (C.81).

`docs/RELEASING.md` is the release routine (`release.10`): versioning, cutting a release, fixing forward, the Claude Code check and the packages checked by hand each release, and the smoke checklist. Dependabot (`.github/dependabot.yml`) proposes openai, electron, electron-builder and electron-updater, and the workflows' actions, quarterly; nothing merges on its own.

Test fixtures stay fit to publish: emails use `@example.com`, and a line with a placeholder profile path (`C:\Users\<name>`, `/home/<name>`) ends with a comment that starts with `check-public: allow`, as does a line with a long dummy key. The marker exempts its own line only, and only right after a comment opener (`//`, `/*`, `#`, `<!--` or a leading `*`), so prose that names it is still scanned.

## Hard rules

1. Never change a manuscript file except through the Save action in `src/main/files.ts`. There is no autosave: the toolbar's Save to chapter, Ctrl+S and the Save in the review dialogs and the leave and close prompts all run the one `saveChapter` (PLAN 6.3). Writes are atomic (temp file then rename) and preserve the file's EOL style, BOM, and trailing newline, and bytes equal to the file's are not written at all. Before a save replaces a file, the bytes it replaces are copied to `<userData>/backups` (`chapterBackupHooks` in `src/main/backups.ts`, PLAN 6.5), never into the manuscript folder or the chapter's own folder; when the copy cannot be made, nothing is written. Main checks every target it is handed: `files:save` refuses the guidelines file and anything but a `.md` or `.txt` chapter that lies in the manuscript folder or was opened from it in this run (`assertSavableChapter`); `reviews:save` writes to the path it is given only when that is a `.review.json` directly in its chapter's folder in the reviews folder and holds no other chapter's review, and puts anything else in a new entry there instead (`saveReview` in `src/main/reviews.ts`). Besides Save, two things may add a file to the manuscript folder, and they only create, so neither can ever modify an existing file: `createChapter` in the same file, which writes with the exclusive-create flag (`wx`), and `ensureGuidelinesFile` in `src/main/guidelines.ts`, which copies the template with `COPYFILE_EXCL`. The one other writer there is the review store, and only when the author keeps the reviews folder inside the manuscript folder (PLAN 6.1): it then saves over, moves and removes its own `.review.json` files, the `.last-open.json` in each chapter's folder and its `.adoption.json` inside that folder, as it would anywhere else, and `listChapters` skips that folder, so none of them is ever a chapter. Everything the author edits inside the app, including text they type themselves, becomes a hunk and reaches the file only through Save.
2. Credentials, two facts. (a) Nothing in the app reads, stores, displays, or proxies Claude credentials. Sign-in happens in the Claude Code CLI or via `ANTHROPIC_API_KEY`; the app only shows instructions and account status from Claude Code's own `initialize` reply and `claude auth status`, keeping only the whitelisted fields (`parseAuthStatus`, `toAccount`), and it never starts a sign-in: `runClaudeCli` runs nothing but `--version` and `auth status --json`. (b) The app stores one credential, the ChatGPT sign-in (`codex.2`, PLAN 5.7). The OpenAI API key it also stored went in `codex.6`: nothing reads a saved key or `OPENAI_API_KEY` any more. The sign-in is OpenAI's documented Sign in with ChatGPT for open-source apps, OAuth with PKCE through the system browser and a loopback port on 127.0.0.1 (`src/main/chatgpt`): its access, refresh and ID tokens are one Electron `safeStorage` ciphertext in `secrets.json` beside `settings.json`, never inside it (`src/main/chatgpt/store.ts`, `src/main/secrets.ts`); no sign-in starts when encryption is unavailable; they are decrypted only in the main process at call time, never displayed and never sent to the renderer, which receives only `ChatGptStatus` (signed in or not, the plan the sign-in named, the account's data settings box); the client id OpenAI issued, the account's id and its email never cross either. Sign out revokes the refresh token at OpenAI and removes the tokens, keeping the registration and the host id. Every write of `secrets.json` goes through `updateSecrets`, which writes only the parts it knows, so the key a file from before `codex.6` still holds is read past, never used, and dropped at the next write, and which never takes a read that failed for an empty file: a file there but unreadable refuses the write, and a damaged one is copied aside as `secrets.json.corrupt-<time>` first or nothing is written; the sign-in's decisions read it as strictly (`readChatGptChecked`), and only a status reads it leniently. Claude's rule (a) is unchanged: this sign-in is OpenAI's, never Claude's.
3. The renderer has no Node access. All file system, watcher, settings, and SDK work goes through typed IPC declared in `src/shared/ipc.ts`.
4. `src/shared` must not import Node or DOM APIs. Every algorithm there gets unit tests, including property-style round trips for compose and rebase.
5. Hunks never overlap, offsets always refer to the review's LF-normalized base text, and the composed output is a pure function of base plus hunk decisions.
6. Claude calls remove every built-in tool (`--tools ""`), load no user settings (`--setting-sources=`), never use `--bare` (it turns off subscription sign-in), and never use the vault as `cwd`. They never set or override Claude Code's client or entrypoint identity (Anthropic's Usage Policy bars services that misrepresent the product or client): no entrypoint, user-agent or header variable, no flag that names a client. `buildClaudeEnv` adds only `CLAUDE_CODE_STARTUP_FAILURE_RESULTS` and passes everything else through unchanged or removes it, and `test/main/claudeOptions.test.ts` pins that. Sign in with ChatGPT likewise names the app as itself, `APP_NAME` as `agent_name_hint` on the first sign-in, and sends no header or parameter that names another client (`codex.2`; the Sign in with ChatGPT terms bar impersonating another application).
7. Keep `PLAN.md` as the source of truth. If a design decision changes during implementation, edit the plan in the same commit.
8. Every user-visible change adds a line under `## [Unreleased]` in `CHANGELOG.md` in the same commit, in the group it belongs to (Keep a Changelog 1.1.0: Added, Changed, Deprecated, Removed, Fixed, Security). Write it for the people who use the app; internal refactors, tests and plan edits get no line.
9. The log (`src/main/log.ts`, `<userData>/logs/main.log`, PLAN 11.3 m, C.84) records what happened, never content: no chapter text, prompt, guidelines, reply, `detail`, draft, backup, account email, key or the key's last four characters, and no ChatGPT token, refresh token, authorization code, client id, state, nonce, PKCE verifier, host id or account id (`codex.2`). A new log call passes an event name and flat scalar fields (string, number, boolean or null); `formatFields` drops any other value whole and scrubs and cuts every string, but that is the backstop, not a reason to pass text. An error goes in only as the fields `loggableErrorFields` gives (`src/shared/diagnostics/redact.ts`, the one policy for errors), spread into the line, never by passing its `message`, `stack` or `String(err)` yourself. A request that fails is already logged as `ipc.failed` by `runHandler` (`src/main/ipcEnvelope.ts`), and a review that fails as `ai.review.failed` by `withLogging`, so a handler need not log its own failure: it throws, with `fail(code, message)` for one the author should read. The policy keeps the message of an app error (of every code but the `*-invalid-output` ones and `claude-refusal`) and the message and stack frames of any other error but a SyntaxError or a file system error, so those words reach the log: a `fail` message, or that of any error main throws, may name a file, but it never quotes chapter text, a prompt, the guidelines or a reply. Put such text in `detail`, which is never logged. Copy diagnostics keeps of a warning only the fields `REPORT_WARNING_FIELDS` lists (C.80), so a new field it should show goes on that list.

- ChatGPT's reviews are tested without an account against `test/helpers/mockOpenAi.ts` (vitest imports it; `node test/helpers/mockOpenAi.ts --port 4599` runs it for the app, started with `MANUSCRIPT_REVIEW_OPENAI_BASE_URL=http://127.0.0.1:4599/v1` beside the sign-in mock below). It answers a bearer that is a ChatGPT sign-in's access token (`chatGptClaims`: a JWT for `https://api.openai.com/v1` granting `chatgpt.tokens.use.direct`, as `mockChatGptAuth.ts` makes them) as OpenAI's pages describe that route (`codex.3`, PLAN 5.8): the model list as a `models` array of `slug`, `display_name` and `visibility` (`CHATGPT_MODELS`), a review only with `store: false`, `stream: true`, `input` as a list without system messages and none of `CHATGPT_REFUSED_PARAMETERS` (each refused as `subscription_sharing_unsupported_capability` naming it), a 401 for a token whose `exp` has passed, and the plan's limits in the `x-codex-primary-*` and `x-codex-secondary-*` headers. Any other bearer, an API key among them, gets a 401 (`invalid_api_key`): no provider sends a key since `codex.6`. The scenario (`chatGptScenarioFor`: the first of `CHATGPT_SCENARIOS` the name holds, in any case) is the access token's `mock_scenario` claim, which the sign-in mock puts in every token it makes once it has a name (`--api-scenario <name>` as it starts, so the first sign-in's tokens carry it, or `POST /mock/api-scenario` for the tokens of the next sign-in or renewal), unless `POST /mock/scenario` with a name on this mock sets one for every ChatGPT request at once (an empty body clears it); a window run picks one either way. The plan's own: `nearlimit` the 5-hour limit 85% used; `weeklylimit` the weekly limit reached; `usagelimit` a 429 for the plan's usage limit with the 5-hour limit reached in its headers, `usagelimitbare` the same with no headers, `usagelimitstream` that limit reached mid-reply; `noheaders` an answer with no limits; `noteligible` a 403; `noschema` a 400 for `text.format`; `unavailable` a 503; `invaliduser` a 401 with the plan's code for every request; `nomodels` an empty list. Those an OpenAI API key's words picked until `codex.6`: `unauthorized` a 401 for every request (`invalid_api_key`); `ratelimit` a 429 (`rate_limit_exceeded`) and `servererror` a 500 for a review, while the model list still answers; `malformed` a reply that breaks off mid-JSON; `prose` a reply written as prose that quotes the chapter (`PROSE_REPLY`, `hardening.3b`); `wrongshape` JSON of the wrong shape; `slow` a streamed reply that trickles out over about seven seconds; `obsidian` the review of `samples/manuscript/Chapter 03 - Obsidian.md` (`OBSIDIAN_REVIEW`, `files.9`); `outputlimit` a reply cut off at the model's output limit, which ends `incomplete` (`files.10`); `unverified` the 400 OpenAI gives a streamed request from an organisation that has not verified its identity, while the model list answers (`UNVERIFIED_STREAM_MESSAGE`, `hardening.10`); `skippedonly` a model list of only gpt-5.5-pro, gpt-5-codex and gpt-5-chat-latest, with gpt-5.5 hidden, whose default is the first, gpt-5.5-pro (`CHATGPT_SKIPPED_ONLY_MODELS`, `hardening.10`, C.82); anything else the canned review of `Chapter 01 - The Flood.md` (`CANNED_REVIEW`), its limits low. To run a review end to end, start both mocks and the app with both switches and `dev:clean --shell-stub`, sign in as the next item says, and tick the data settings box. A sign-in kept from an earlier run of the sign-in mock names a registration a restarted one does not know (it answers "unknown client"), so sign in again with Use another account, or start on a new data folder.

- Development switches are read only in `src/main/devSwitches.ts` (`readDevSwitches`, PLAN 11.3 b, C.39).
